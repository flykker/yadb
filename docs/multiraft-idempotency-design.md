# Proposed Multi-Raft correctness gates 3 and 4

Design first; three slices are now implemented, the rest is not. Scope is the OpenRaft HTTP paths, not legacy Raft or production readiness. Existing evidence and unresolved failures are in `docs/multiraft-production-todo.md` and `docs/multiraft-verification.md`.

Implementation status (2026-11-15):

- **Gate 3, control scope only — implemented.** `Idempotency-Key` on `POST /v1/apply`, the committed/fenced record in `/sys/idempotency/<subject-hash>/<key-hash>`, the single `RevisionTxn` that commits the control-state mutation and the record together, replay, `409` conflict/fenced, and `POST /v1/idempotency/resolve` exist in `crates/yadbd/src/main.rs` (`apply_dispatch`, `handle_resolve`, `read_record`, `replay_record`). Record reads use the pre-existing quorum-confirmed `LocalMetaKv::try_linearizable_control_snapshot`; plain `try_snapshot` is never used for a record. Verified live against the local deployment: unsigned 401, forged 401, non-admin 403, admin 200; keyed apply 200 with `generation` +1, replay 200 with unchanged `generation`, same key/different payload 409, resolve `committed`, fresh resolve `not_committed`, apply after fence 409, bad scope 400; records survived two clean restarts.
- **Gate 3, project scope — block UNMAP implemented (2026-11-15).** `POST /block/{project}/{volume}/unmap` accepts `Idempotency-Key`; SQL, S3 object PUT/DELETE and block PUT still reject one with 501. UNMAP is first because it has no staging: it changes only the extent map, so `BlockVolumeEngine::unmap_at_with` publishes the map and appends the caller's guards and ops to the *same* `RevisionTxn` (`crates/yadb-block/src/lib.rs`: `MapPublication`, `publish_map_with`). The record is project-scoped (`/idempotency/<project-id>/<subject-hash>/<key-hash>`) and the admission counter is **group**-scoped (`/idempotency/g<group-id>/_usage`), because the limit it enforces is the group's state image and a transaction cannot span groups; `GroupRouter` (`openraft_client.rs`: `GROUP_IDEMPOTENCY_NAMESPACE`, `group_idempotency_namespace`, `group_idempotency_usage_key`, `group_idempotency_namespace_for_project`) validates both against the router's own group map, so a caller cannot mint a key that routes elsewhere. `handle_resolve` now accepts `{"scope":"project","project":"<name>","key":"<k>"}` and fences in the project group, authorizing the verified subject for `readWrite` on that project rather than requiring admin; a control resolve rejects a `project` field and a project resolve rejects a missing one. Quota exhaustion on a fresh mutation is `429` before the map is read; on a fresh resolve it is `503 unknown/capacity_exhausted`, never `not_committed`. Remaining gaps are listed in "Atomic commit, replay, and limits" and in the production todo.
- **Gate 3, replicated quota — implemented.** Every keyed `POST /v1/apply` and every fresh-key `resolve` commits one `IdempotencyUsage` counter at `/sys/idempotency/_usage` in the *same* guarded `RevisionTxn` as the record (`expected_mod_revision` on the counter, `main.rs`: `IDEMPOTENCY_USAGE_KEY`, `ApplySnapshot`, `read_apply_snapshot`, `idempotency_usage`, `idempotency_quota_response`). Admission is `10_000` records or `8 MiB` of encoded records, and the byte budget is the binding limit, deliberately far below `MAX_IMAGE = 64 MiB` so the counter trips while the image is still serializable. An inadmissible request is refused with `429` before planning and before any side effect is staged, and a `resolve` of a fresh key draws from the same budget because fencing a key is a permanent record. Records written before the counter existed are counted once by a scan when the key is absent; the guarded put means only one concurrent first writer can install it. Verified by unit tests for both ceilings and for counter decoding; the `429` path itself is not yet exercised end-to-end against a live cluster.
- **Gate 4 — primitive implemented; block reads consume it.** `LocalMetaKv::try_linearizable_snapshot` and `GroupRouter::linearizable_snapshot` provide a group-routed quorum-confirmed snapshot with the same single-group and trailing-separator validation as `try_snapshot`. One HTTP path consumes it: OpenRaft block reads with `consistent=true` (including the iSCSI read path) read the extent map through it on the project-group leader and then fetch immutable blobs (`BlockVolumeEngine::read_at_consistent`). SQL, S3 and `/v1/status` still serve the locally applied state, so the rest of the table below remains the "Today" column.

## Gate 3 — Proposed idempotency and outcome resolution

### Wire contract and scope

**Proposed:** accept exactly one `Idempotency-Key` header on `/v1/apply`, mutating `/db/{project}/{database}/query`, S3 object PUT/DELETE, and block PUT/UNMAP. Its value is 1–128 ASCII bytes from `[A-Za-z0-9._~-]`, case-sensitive; reject duplicates, whitespace, invalid bytes and oversize with 400 before any side effect. Absence preserves existing behavior, including ambiguous-write warnings. A key on a non-mutating SQL request is rejected with 400. Keyed operations require OpenRaft and a verified subject; otherwise return 501 or 401 respectively before side effects. Existing `extract_subject` can use unverified labels, so **requires change in `yadbd`** (`main.rs:928–981`).

Scope is `(control | immutable project ID, verified subject, key)`, across endpoints within that scope; not per endpoint, so reuse on a different endpoint conflicts. Control apply requires the existing admin check; project lookup/replay requires current write authorization, not merely possession of a key. Hash length-prefixed UTF-8 fields with SHA-256 for storage path components; preserve a versioned request fingerprint covering method, canonical decoded target and semantic query parameters, content type where relevant, exact body bytes, and SQL session/transaction options. Hash the original payload, not the reserialized forwarding body; alternatively define canonical JSON and use it identically at both hops. The former requires forwarding original bytes. Domain-separate fingerprint versions and reject mismatch with 409 `{"error":"idempotency_key_conflict"}`. Cryptographic hash collisions are an explicit assumption.

**Requires change:** `/v1/apply` and SQL currently extract JSON then reserialize for forwarding (`handle_apply`, `handle_db_query`); the raw proxy forwards only selected headers (`proxy_http_to_peer`). Preserve key, original fingerprint inputs, authentication and the complete recorded response allowlist end to end. The owner leader validates again. S3-wire constructs fresh gateway headers and translates success/errors (`protocols/s3.rs:420–495, 614–660`); carry the key and record/replay the *external* response, including ETag and relevant content type, rather than silently changing the S3 result. Never trust a client-supplied internal fingerprint or forwarded marker as authentication. Preserve `x-yadb-leader-id`; proxy failure after sending remains unknown, not an automatic resubmission (`maybe_forward_write`, `forward_error_response`). `yadbctl` currently discards response headers and has no key/status options (`yadbctl/src/main.rs:210–277, 465–482, 585–608`): add explicit key and outcome commands/header reporting, without automatic retry.

### Atomic commit, replay, and limits

**Proposed:** store a versioned outcome record under `/sys/idempotency/<subject-hash>/<key-hash>` for control, or `/idempotency/<project-id>/<subject-hash>/<key-hash>` for project data. **Routing prerequisite implemented (2026-11-15):** `GroupRouter::group_id` (`openraft_client.rs`) now routes `/idempotency/<canonical-project-id>/…` by project ID, and `group_id_for_project` / `idempotency_namespace` return the group and namespace for a project, failing closed with `MetaError::Routing` for an unmapped or non-canonical project instead of falling back to control. Project records cannot live under `/sys/`: `group_id` sends every `/sys/` key to the control group, so a `/sys/idempotency/p/<project>/…` record would be written to a group that never resolves it. **Implemented for block UNMAP (2026-11-15):** `POST /block/{project}/{volume}/unmap` writes and reads such a record, and its admission counter lives at `/idempotency/g<group-id>/_usage` (`group_idempotency_namespace`, `group_idempotency_usage_key`, `group_idempotency_namespace_for_project`). The counter is group-scoped rather than project-scoped because the limit it enforces is the group's state image and a transaction cannot span groups, so two projects mapped to one group share one budget by design. SQL, S3 and block PUT still write no project-scoped record. `group_for` still rejects cross-group operations. Record fingerprint, `committed` or `fenced`, and for committed operations the exact bounded external HTTP status, body bytes (base64) and selected end-to-end headers. Re-authorize before revealing or replaying a record. Do not persist secrets or authentication headers.

On the owner leader, check for a record before planning or external staging. For an absent key, stage a deterministic result and submit **one** `KvCommand::RevisionTxn`: retain all existing mutation `RevisionGuard`s, add a guard on the outcome key with `expected_mod_revision: 0`, and add `TxnOp::Put` of the complete response record to the same ops as the mutation. `MetaStateMachine::apply` checks all guards before applying any op under one revision (`kv.rs:47–88, 223–237, 323–369`); durable snapshots contain KV state (`kv.rs:167–183`). On `TxnOk`, return exactly the stored response. On `CasConflict`, quorum-read the record: matching committed record means replay without re-execution; mismatched fingerprint means 409; fenced means 409 `{"error":"idempotency_key_fenced"}`. If absent, a mutation guard conflicted: replan only when no irreversible effect has occurred, otherwise return a safe error. Never infer which guard failed from `current_version` (`KvResult::CasConflict` has no guard identity).

**Requires change in each engine:** `handle_apply` already builds a guarded control transaction (`main.rs:1782–1857`); include the response from `ControlPlaneState::plan` in that transaction. Generation increments only on a changed plan, whereas KV transaction revision increments independently even for unchanged state (`yadb-control/src/lib.rs:234–359`, `kv.rs:323–367`). SQL, S3 and block PUT must expose a single final atomic publication transaction, prepared response and guards to the idempotency layer; block UNMAP now does (`MapPublication` / `unmap_at_with`, see the status list above). SQL contains multiple transaction paths and stateful sessions (`yadb-db/src/lib.rs:403, 759–919, 1262`; `handle_db_query`); reject keyed scripts/sessions not proven to publish all their visible effects in one transaction **before** execution. Do not advertise full SQL coverage until implemented. S3 has upload intent/staging and a final metadata transaction (`yadb-s3/src/lib.rs:192, 338, 458, 523–551`); block and SQL likewise stage data outside metadata. Staging may leave unreachable blobs/intents or sequence allocations after a crash: they are not a committed user mutation, need safe cleanup, and cannot be called exactly-once external side effects. Publication must reference durable readable immutable data before the Raft transaction; no post-commit response-dependent effect may be required. If a result cannot be known and bounded before publication, reject the keyed operation before side effects; existing primitives cannot atomically store a response computed from the returned Raft revision. No metadata mutation may commit separately from the record.

**Proposed bound:** maximum 16 KiB serialized outcome including at most 8 KiB response body; reject before publication if exceeded. Permanently retain committed and fenced records in this first gate; enforce a replicated per-scope quota of 10,000 records, atomically guarded and updated in the same transaction, rejecting new keys with 429 before staging when full. Existing-key replay/lookup still works at capacity. **Requires change:** quota reservation and concurrent pre-staging admission must be designed so reservations themselves have bounded durable lifecycle; if unavailable, reject before staging rather than claiming the quota is enforced. No automatic GC or key reuse: deleting tombstones makes old delayed requests unsafe. This finite quota trades availability for an actual bound; reclamation requires a separately designed durable epoch/watermark protocol and clients that cannot submit old epochs. The total cluster bound additionally depends on bounded provisioned scopes. Raft log/state-image limits and staged-blob capacity remain separate (`multiraft-production-todo.md`, sections 1 and 3).

### Definite status via a fence

**Proposed:** `POST /v1/idempotency/resolve` with authenticated JSON `{"scope":"control","key":"K"}` or `{"scope":"project","project":"name","key":"K"}`. This is intentionally a state-changing resolve, not a cacheable GET. On the owner leader, issue a create-only `RevisionTxn` for a permanent `fenced` record if absent; on conflict read the winner with a quorum-confirmed snapshot. It serializes with every mutation's absent-key guard: if mutation wins, resolve returns committed; if fence wins, every delayed or in-flight mutation loses its guard. A plain barrier plus missing record is insufficient because an earlier queued request can commit afterwards (`openraft_client.rs:689–713`). Quota admission applies to fences too; if a fence cannot be durably committed, answer unknown, never not_committed. A fence burns the key; use a new key to issue a new request.

Exact JSON response shapes (all fields shown):

* HTTP 200: `{"outcome":"committed","reason":null,"response":{"status":200,"headers":{"content-type":"application/json"},"body_base64":"..."}}` (actual status/allowlisted headers/body as recorded; empty body is `""`).
* HTTP 200: `{"outcome":"not_committed","reason":"fenced","response":null}` means no keyed publication won and none can later win for this key, not that no staging happened.
* HTTP 503: `{"outcome":"unknown","reason":"quorum_unavailable","response":null}`; reason is one of `quorum_unavailable`, `leader_unavailable`, `fence_outcome_unknown`, `capacity_exhausted`, `storage_unavailable`. A timeout of the fence is itself unknown; repeat resolve safely. Auth errors are 401/403, invalid scope/key 400, unknown project 404; none asserts an outcome. Expired authorization prevents disclosure, not a false negative.

The record and mutation are ordered in the same applied Raft entry: a lost client response after commit is resolved to its exact response after quorum recovery/restart. A committed mutation with a lost record is excluded only if all publication paths satisfy the single-transaction rule and storage/consensus durability assumptions hold. Before submission, a crash may leave only staging; after an unknown submission, resolve may fence or observe the winner. During partition, unavailable quorum, storage corruption, or unresolved fence write, the answer is unknown. No guarantee covers disaster loss of a quorum, unkeyed requests, external side effects, or requests rejected from the keyed contract.

### Rejected alternatives

* Local cache, separate control-group record, or write-after-mutation: crash or cross-group failure separates the result from the mutation.
* Return not_committed on missing quorum-read key: an already queued proposal can still commit. Time-based deletion/TTL also permits late duplicates.
* Automatically retry unknown unkeyed requests: `OpenRaftWriteUnknown` expressly does not prove rollback (`openraft_client.rs:653–672`; `meta_err_response`).

### Gate acceptance criteria

**Proposed tests:** for every supported endpoint and direct/follower route, verify absent-key compatibility, validation/auth, exact status/body/ETag replay, cross-endpoint/payload conflict, concurrent identical and different payloads, guard conflicts, capacity, and no re-execution/publication. Inject response loss after publication, resolve on another node, assert committed and replay; crash/kill the leader, elect/reopen and assert record plus mutation survive together. Race resolve against queued and submitted mutations in both orders, including delayed old-leader work and a lost fence response; not_committed must preclude later publication. Test pre-publication staging crash, unknown quorum loss/recovery, scope isolation and safe quota exhaustion. Capture command IDs, injection point, leader/quorum and durable outcomes per `multiraft-verification.md` required failure record format. Passing these closes only this scoped HTTP gate, not power-loss, storage-contract, protocol, GC or production gates.

## Gate 4 — Proposed opt-in read barrier

### Current and proposed promises

| Path | Today | Proposed with selector |
| --- | --- | --- |
| SQL SELECT | Locally applied metadata; `force_leader` routes but is not a barrier (`handle_db_query`; `raft.rs:586–590`). | One project-group linearizable snapshot for a supported read-only statement; reject unsupported session/multi-statement cases until one-snapshot semantics exist. |
| S3 GET/LIST | Local metadata; native range GET can head and fetch separately (`handle_s3_get`); S3-wire uses its own head/manifest (`protocols/s3.rs:345–350, 498–582`). | One project-group snapshot of manifest or listing; range, conditions, headers and bytes derive from that same manifest. Each LIST page is separate, not a cross-page snapshot. |
| Block read | Default locally applied. OpenRaft `consistent=true` forwards to the project-group leader and reads the extent map through `try_linearizable_snapshot`, then fetches the immutable blobs named by that map; a missing/tombstoned blob is a `503`, never zeros (`handle_block_read`, `BlockVolumeEngine::read_at_consistent`). Legacy mode unchanged. | Same mechanism; the remaining gap is that the map snapshot does not fence blob GC, so a collected blob is a definite failure rather than a retryable stale read. |
| `/v1/status` | Local cached control clone, no barrier (`handle_status`). | Control-group linearizable snapshot of `CONTROL_STATE_KEY`; no claim of data-group status or globally atomic view. |

**Proposed:** `x-yadb-read-consistency: linearizable`; missing header leaves all existing behavior unchanged. Reject duplicates/unknown values with 400. `consistent=true` already carries this meaning for OpenRaft block reads and keeps legacy behavior unchanged. A write-containing SQL script with this selector is rejected 400, not partially executed. On unavailable quorum/leader return 503, never a stale fallback; unsupported backends/operations return 501. S3-wire errors must remain S3 XML and preserve meaningful 503 rather than convert storage failure to NoSuchKey (`protocols/s3.rs:503–509`, `map_error`).

### Mechanism and blockers

**Requires change in `openraft_client.rs` and `raft.rs`:** expose group-routed `try_linearizable_snapshot(keys, prefixes)` through `LocalMetaKv`, enforcing the same single-group validation as `GroupRouter::try_snapshot`. Existing `OpenRaftClient::linearizable_snapshot` calls `ensure_linearizable`, then copies state, rejects followers and times out at one second (`openraft_client.rs:722–769`); only control is currently exposed (`raft.rs:971–985`). Run blocking bridge calls off Tokio workers. Each opt-in read pays a leader hop when needed, a quorum confirmation and snapshot copy, plus data I/O; availability depends on both group quorum and data. Preserve the selector, credentials, path/query and response headers through a bounded read proxy; forward once to the addressed group leader, which repeats authorization and barriers. A follower cannot use the present leader-only primitive to serve locally. On leadership change, return error rather than loop or fall back.

**Requires change in SQL/S3/block engines:** thread the owned snapshot into every metadata read used to form a result, including table/index discovery and all relevant prefixes. A barrier followed by independent local `get`s is not a transaction-wide snapshot and can mix revisions (`kv.rs:15–20`; `yadb-db/src/lib.rs:579–602`). For range GET, eliminate the independent head/fetch race. For block, the map snapshot and "a missing referenced blob is an error" rule now exist (`read_at_consistent`, `BlockError::Inconsistent`); what remains is that reclamation is not pinned, so a replaced-and-collected block makes the read fail rather than succeed. S3 GC is currently disabled (`multiraft-production-todo.md`, current status); enabling it later requires snapshot pinning or equivalent safe reclamation. Failure to fetch referenced bytes must fail, not serve older data. SQL/session semantics and multi-shard metadata selection require an explicit audit before enabling the selector.

Control authorization remains governed by the existing separately refreshed control lease, not the project-group barrier (`main.rs:499–510`; `multiraft-verification.md` authorization freshness). A lease may remain valid after quorum loss until expiry and does not guarantee instantaneous revocation; do not advertise a globally linearizable authorization-plus-data transaction. For `/v1/status`, read the barrier snapshot directly rather than the cache; do not extend an authorization lease merely because a different group's barrier succeeded. There is no cross-group atomic snapshot. PG uses its own HTTP bridge and maps non-403 errors to `XX000` (`protocols/pg.rs:201–235`); iSCSI issues `consistent=true` and maps failure to sense (`protocols/iscsi.rs:585–606`). Neither gains an idempotency key or a new wire consistency promise automatically; qualify them separately.

### Rejected alternatives

* `force_leader` or a recent heartbeat alone: neither confirms current quorum nor pins the data snapshot.
* Barrier on control group for project data, or separately barrier each shard: neither supplies one atomic project snapshot.
* Serve a stale follower after the leader barrier without a verified applied-index wait and pinned snapshot: current API provides no such follower guarantee.

### Gate acceptance criteria

**Proposed tests:** hold a follower behind after an acknowledged write; default read may show its local view, while selected SQL, S3 GET/range/LIST and block reads through it return the committed version via the data leader, and selected status returns fresh control state. Isolate the leader or remove quorum: selected reads return 503 within configured bounds, never stale success; exercise unknown leader, leader change, malformed selectors and forwarding loops. Race overwrite/delete against multi-key reads, range HEAD and blob fetch; assert one coherent revision or an explicit failure, including safe blob retention. For OpenRaft block reads, `consistent=true` and the iSCSI read path are exercised through a live follower forward and return the committed bytes; the missing-blob case returns `503` rather than zeros. Test control lease expiry separately and demonstrate it is not a data barrier. Record exact topology, histories and failure boundaries; these tests establish only the exercised single-group read contract, not cross-group serializability, security revocation bounds or production readiness.
